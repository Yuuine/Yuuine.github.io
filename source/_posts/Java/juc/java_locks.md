# 锁

## 前言

在多线程和并发场景下，如何保证数据的安全性和一致性？锁机制正是解决这一问题的关键技术之一。

Java 提供了多种锁的实现方式，从最基本的 `synchronized` 关键字到更高级的显式锁（如 `ReentrantLock`），再到各种读写锁、条件变量等，形成了一个完整的并发控制体系。

下文将从不同的角度对锁进行分类，介绍 Java 中的锁实现。

## 锁的分类

### 按是否阻塞分类

**悲观锁**

核心思想是：假设最坏的情况一定会发生，即认为并发访问必定会产生冲突，在访问共享资源前必须先加锁，确保独占。

在 Java 中，**所有基于阻塞的互斥锁本质上都是悲观锁**，因为在操作之前就获取锁，阻止其他线程进入临界区。

示例：
> `synchronized`
> `ReentrantLock`
> 数据库行锁、表锁

下文会详解 `synchronized` 和 `ReentrantLock`。

**乐观锁**

核心思想是：假设最坏的情况不会发生，即认为并发修改大概率不会冲突，因此不加锁，而是在提交更新时检查数据是否被他人修改过。若被修改，则失败重试或报错。

Java 中基于版本比对或 CAS 实现乐观锁，冲突时通过重试机制解决。

Java 并发包大量使用 CAS 实现无锁并发：
| 类 | 说明 |
|----|------|
| `AtomicInteger` | 基于 `Unsafe.compareAndSwapInt()` |
| `AtomicReference` | 支持对象引用的 CAS |
| `ConcurrentHashMap` | put 操作中使用 CAS + synchronized（锁单个 Node/桶） |
| `StampedLock`（乐观读） | 支持 tryOptimisticRead() |



对比：
| 维度    | 乐观锁                     | 悲观锁            |
|-------|-------------------------|----------------|
| 并发模型  | 无锁、非阻塞                  | 加锁、阻塞          |
| 适用场景  | 读多写少、冲突少（如点赞、浏览）        | 写多、强一致（如支付、库存） |
| 性能    | 高吞吐（无上下文切换）             | 高冲突下性能骤降       |
| 失败处理  | 需重试机制（如 for 循环 + sleep） | 阻塞等待，无显式失败     |
| 实现复杂度 | 需处理重试、ABA 问题            | 逻辑简单，但需防死锁     |
| 跨 JVM | 难（需 DB 或 Redis 支持）      | 可通过分布式锁实现      |

### 按锁的实现方式分类

**内置锁(JVM层)**

例如 `synchronized` 锁，由 JVM 实现，控制自动获取锁和释放锁。

**显式锁(JUC层)**

基于 `Lock` 接口实现，如 `ReentrantLock` ，需要手动获取锁和释放锁。

---

### 按是否可重入分类

**可重入锁**

可重入锁是指同一个线程可以多次获取同一把锁而不会发生死锁。每次加锁，锁的“持有计数器”+1；每次释放，计数器-1；直到计数器归零，锁才真正释放。

可重入锁支持递归调用，支持继承和组合，Java 中的锁基本上都属于可重入锁。

**不可重入锁**

不可重入锁是指同一个线程一次只能获取一把锁，再次加锁会发生阻塞。

Java 中基本不用不可重入锁，了解即可。

---

### 按读写维度分类

**互斥锁**

同一时刻只允许一个线程访问共享资源，无论该线程是“读”还是“写”。 也称为 排他锁（Exclusive Lock） 或 写锁（Write Lock）。

特点：
> 强一致性保障：完全串行化访问。
> 简单可靠：逻辑清晰，不易出错。
> 性能瓶颈：即使多个线程只是“读”，也必须排队。

**读写锁**

读写锁又分为**读锁（共享锁）**和**写锁（排他锁）**，多个线程可以同时获取读锁（并发读），但同一时刻只能有一个线程获取写锁（写时禁止其他线程读或写）。

简单来说，读写互斥、写写互斥，读读不互斥。

Java 中 `ReentrantReadWriteLock` 就是一个读写锁（JUC 提供）。
> `readLock()` 返回读锁 `ReadLock`
> `writeLock()` 返回写锁 `WriteLock`

均基于 AQS 实现， 内部用一个 `int` 的高16位存读锁计数，低16位存写锁计数。

tips：Java 允许**写锁**到**读锁**的锁降级，用于保证数据的可见性。

示例：
```java
writeLock.lock();
try {
    data = fetchDataFromDB(); // 更新数据
    
    // 降级：先获取读锁，再释放写锁
    readLock.lock();
} finally {
    writeLock.unlock(); // 释放写锁，但仍有读锁
}

try {
    // 此时其他线程可并发读，但不能写
    useData(data);
} finally {
    readLock.unlock();
}
```

### 按公平性分类

**公平锁**

核心思想是“先来后到”原则：

当锁被释放时，等待时间最长的线程优先获取锁。

**非公平锁**

核心思想是“插队优先”原则：

当锁被释放时，新来的线程可以直接尝试抢占锁，而不必排队。 只有抢占失败，才加入等待队列尾部。

以`ReentrantLock`为例，默认情况下是**非公平锁**，可以通过构造函数指定公平锁。

```Java
// 非公平锁（默认）
ReentrantLock nonFairLock = new ReentrantLock(); 

// 公平锁
ReentrantLock fairLock = new ReentrantLock(true);
```

> `synchronized` 锁始终是非公平的。

## 自旋锁和自适应自旋锁

阻塞或唤醒一个 Java 线程需要操作系统切换 CPU 状态来完成，这种状态转换需要耗费处理器时间。如果同步代码块中的内容过于简单，状态转换消耗的时间有可能比用户代码执行的时间还要长。

在许多场景中，同步资源的锁定时间很短，为了这一小段时间去切换线程，线程挂起和恢复线程花费的时间可能会让系统得不偿失。如果物理机器有多个处理器，能够让两个或以上的线程同时并行执行，我们就可以让后面那个请求锁的线程不放弃 CPU 的执行时间，看看持有锁的线程是否会很快释放锁。

为了让当前线程“稍等一下”，我们需要让当前线程进行自旋，如果在自旋完成后前面锁定同步资源的线程已经释放了锁，那么当前线程就可以不用阻塞而是直接获取同步资源，从而避免切换线程的开销。这就是自旋锁。

自旋锁本身是有缺点的，它不能代替阻塞。自旋等待虽然避免了线程切换的开销，但它要占用处理器时间。如果锁被占用的时间很短，自旋等待的效果就会非常好。反之，如果锁被占用的时间很长，那么自旋的线程只会白白浪费处理器资源。所以，自旋等待的时间必须要有一定的限度，如果自旋超过了限定次数（默认是 10 次，可以使用 `-XX:PreBlockSpin` 来更改）没有成功获得锁，就应当挂起线程。需要注意的是，JDK 6+ 引入了自适应自旋锁，自旋次数不再固定，而是由 JVM 根据上次自旋结果动态调整。

自旋锁的实现原理同样也是 CAS，`AtomicInteger` 中调用 `unsafe` 进行自增操作的源码中的 `do-while` 循环就是一个自旋操作，如果修改数值失败则通过循环来执行自旋，直至修改成功。

自旋锁在 JDK 1.4.2 中引入，使用 `-XX:+UseSpinning` 来开启。JDK 6 中变为默认开启，并且引入了自适应的自旋锁（适应性自旋锁）。

自适应意味着自旋的时间（次数）不再固定，而是由前一次在同一个锁上的自旋时间及锁的拥有者的状态来决定。如果在同一个锁对象上，自旋刚刚成功获得过锁，并且持有锁的线程正在运行中，那么虚拟机就会认为这次自旋也是很有可能再次成功的，进而它将允许自旋等待更长的时间。如果对于某个锁，自旋很少成功获得过，那在以后尝试获取这个锁时将可能省略掉自旋过程，直接阻塞线程，避免浪费处理器资源。
